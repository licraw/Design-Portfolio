## What it is

Soft Arcade is a portal with several games built independently of each other. They looked related — dark canvas, charcoal surfaces, cream text, cyan action — but nothing was shared. Buttons, inputs, dialogs and tabs were re-implemented inside each game.

Liam audited the production interface and consolidated it into a baseline system. The starting position matters: this was extraction, not a redesign. Nothing in the system was invented because it would look better.

## The audit came first

Eight themes, each separating what was observed in the shipped product from what the system does about it. The evidence was the real thing: the global stylesheet, both game CSS modules, and rendered captures at the viewports the products actually use.

<Figure
  src="/images/projects/soft-arcade-design-system/design-system-audit-themes.png"
  alt="Audit page with eight themed cards — typography, color, spacing and shape, components, interaction, responsive, accessibility, state coverage — each tagged consistent, inconsistent, partial or deferred"
  caption="Each theme is tagged for what it is, not what it should be. Some resolve into the baseline; some are explicitly deferred."
/>

The tags do real work. Color was found consistent in intent but inconsistent in execution — several near-duplicate darks filling the same role. Spacing was mostly reliable, with a handful of one-off values. Accessibility was partial: focus rings existed on prominent links and cards but not on navigation links or several game buttons, and some targets fell below 44px.

## Foundations

Observed values were collapsed into semantic ones rather than catalogued. Nine text styles replaced a set of near-duplicate display sizes; a ten-step spacing scale absorbed the isolated 6, 10, 14, 22 and 34px values; semantic color tokens alias a smaller set of primitives so games consume roles rather than hex.

## Components with their states

The components documented are the ones already repeating across surfaces — the header, cards, panels, buttons, inputs, dialogs and tabs. What the system adds is explicit variants and states, so behavior is reviewable instead of incidental.

<Figure
  src="/images/projects/soft-arcade-design-system/design-system-component-button-states.png"
  alt="Button component documented across variants and states including default, hover, pressed, focus and disabled"
  caption="Hover, pressed, focus and disabled were the treatments varying most widely between games. They become variants rather than per-game CSS."
/>

## Patterns, where components are not the right unit

Some repeated things are compositions, not components. Those are documented as patterns so games can follow the shape without being forced into a component too generic to be useful.

## The system was used, not shelved

[Soft Arcade Synth Lab](/work/soft-arcade-synth-lab) is a new product designed on this baseline. It inherits the foundations and the shared components, and it exposed four gaps — a generic segmented control, a toggle, an anchored popover and a reusable range control. Those are recorded as candidates rather than added to V1, because promoting a component on one consumer is how a system starts describing a single product instead of several.
